# Historical Stripe Premium and channel payments

This is a historical implementation record for payments already created through Stripe. It does not authorize new Stripe checkout or describe current CryptoRails pricing. Preserve webhook/refund/dispute reconciliation and owned billing management for those historical customers. Current purchases follow [CryptoRails](../CRYPTORAILS.md).

# Platform Premium

Premium is one USD monthly subscription covering Premium/member-only videos across all creators. Free videos remain free. Private, blocked and deleted publications remain unavailable to other viewers. Publication audience value `members` is retained in storage/API compatibility and now means platform Premium, not a channel subscription.

`BILLING_ENABLED=true`, a Stripe secret, and a reviewed `PREMIUM_PRICE_CENTS` between 100 and 100000 are required for new checkout. Price defaults to zero, keeping checkout disabled. Terraform exposes `billing_enabled` and `premium_price_cents`, both disabled by default; local compose receives settings through `.env.cloud`. An explicit price is configuration, not permission to enable payments before processor/legal approval. Existing provider subscriptions retain their provider price; changing the configuration only affects new checkout sessions.

## API

- `GET /v1/premium`: public configuration plus the current durable viewer entitlement (`enabled`, `price_cents`, `currency: usd`, `interval: month`, `active`, `status`, `paid_through`). Anonymous viewers have no active entitlement. Authenticated requests check PostgreSQL, not Redis.
- `POST /v1/premium/checkout`: authenticated, verified account; JSON `{}` and stable `Idempotency-Key` of 8–200 characters. Returns `{url}` for Stripe Checkout. The server owns the price/model, monthly recurrence and metadata. Same-key retries reuse the frozen checkout; distinct pending sessions are serialized. Local age is never proof that a previous purchase was unused: before another key can create a subscription, every older provider session/subscription is reconciled. Only provider-confirmed unpaid expiry, an incomplete-expired subscription, or a canceled subscription with no remaining paid period permits another purchase. Missing/ambiguous provider responses block new purchases for operator reconciliation. Expired grants with a still-renewable provider subscription must use the billing portal instead of creating a duplicate subscription.
- `POST /v1/premium/manage`: authenticated JSON `{}`; returns an owned Stripe billing-portal `{url}`. This remains available for existing subscriptions when new sales are disabled. Configure the Stripe portal for cancellation and payment-method management of the single Premium product only. Plan/price changes, discounts, quantity changes and prorations are unsupported: the invoice handler requires the exact frozen USD price. a missing provider portal configuration returns an unavailable error. The API derives the customer from the stored user's provider subscription and verifies its checkout metadata. Client-supplied customer/subscription IDs are never accepted.

Production clients use `/api/v1` aliases as configured by the application gateway. Cancellation changes at the provider are reconciled through subscription webhooks; already paid access lasts until its paid-through timestamp. A refund revokes the refunded period, including partial refunds under the current conservative access policy. Refunds do not perform automatic creator transfers or create platform credits. An open/lost Premium charge dispute suspends new playback grants; successful resolution restores only independently valid, unrefunded paid access. Previously issued media cookies expire within their existing five-minute window.

## Provider processing and accounting

After verifying the Stripe signature, dispatch `processPremiumWebhook` before credit purchases, channel membership reconciliation and dispute handlers. It returns `handled=false` for unknown legacy payments and owns its receipt transaction. Subscribe to checkout completion/async success, `invoice.paid`, subscription lifecycle, `charge.refunded`, and charge dispute created/updated/closed events. HTTP calls pin Stripe API version 2024-06-20; verify webhook endpoint payload compatibility in staging. Modern invoice subscription-parent fields are supported and missing payment-intent correlation is retrieved through the pinned invoice API. Uncorrelatable payments fail closed and require reconciliation.

Only a correlated paid invoice grants access. A success-page redirect never grants Premium. Invoice IDs, payment intents, provider subscription IDs and webhook receipts are unique durable records. Duplicate/reordered invoices cannot mint access beyond the maximum paid-through timestamp or resurrect a refunded period. Refunds record cumulative amounts and apply only new deltas. Provider state is re-read for disputes so delayed events do not reapply an outdated hold.

Premium receipts are platform subscription revenue records. They create **no per-invoice creator earning**. Creator rewards remain a separately approved, capped contribution pool with validated watch weights and reconciled accounting inputs. Money movement, accounting recognition and eligibility must be reviewed before enabling rewards/payouts; a Premium invoice is never automatically divided among channels.

## Legacy and deployment

Migration `019_premium.sql` preserves all channel memberships, checkout records, invoices, refunds and earnings. It disables channel plan sales. `/memberships/checkout` and creator membership-plan handlers return 410; legacy payment webhook reconciliation remains available. Existing channel payments do not silently become global Premium or get erased. Handle any customer transition, cancellation or refund decision through an explicit reviewed operational policy.

Run the explicit migration command with owner credentials, re-provision restricted runtime grants for the new tables, then deploy API/worker/frontend. Keep `PREMIUM_PRICE_CENTS=0` until staging verifies separate-account isolation, cross-creator Premium access, direct media denial, duplicate webhook delivery, expiry, cancellation, refund/replay, dispute holds and customer-portal ownership. PostgreSQL/mock-Stripe tests exercise these mechanics without charging real customers; they do not prove a live provider rollout.
